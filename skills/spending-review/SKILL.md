# 消费结构复盘

## 为什么要分步

一次性把所有类目 × 所有月份都查出来，中间结果会塞满上下文，而其中绝大部分
对结论没有贡献。分步做，每步只把**结论**带进下一步。

## 第一步：摸清结构 —— **不要派子助手**

```
query_transactions(group_by="category")
describe_data()
```

**这一步的结果你自己已经看到了，所以不要派子助手。** 派出去等于把它查的东西
又隔离掉，你还得再问一遍 —— 白白多一次调用。

从结果里挑出**占大头的 3 到 5 个类目**。后面的深挖只针对它们。
占 1% 的类目分析得再细，对用户也没有意义。

## 第二步：逐类目深挖 —— **这一步才派子助手**

对第一步挑出来的每个类目，调一次 `investigate`：

```
分析 2025-09 到 2026-08 的「餐饮外卖」这一类：
逐月金额和笔数、有没有明显的趋势或突变、单笔最大的是哪一家。
直接给结论，不要罗列每个月的数据。
```

**每个子任务必须自足**：时间范围、类目名、要什么口径，全写进去。子助手看不到
你上一句话，也看不到你第一步查到了什么 —— 写得含糊它只能猜，而猜出来的结论
拿回来你也没法判断对不对。

**为什么这一步值得隔离**：每个类目要查十几次（逐月、看趋势、找极值、追一两笔
异常），这些中间结果对最终结论没有贡献，留在对话里只会一直占地方，
而且后面每一轮都要重新发一遍。

## 第三步：综合 —— **不派子助手**

把子助手带回来的结论，和你第一步拿到的整体结构合起来。做三件事：

1. **分开固定项和浮动项**。房租、订阅这类动不了的，和餐饮、购物这类能调的，
   可行性差着量级。混在一起排「省钱榜」毫无意义。
2. **找变化**。哪一类在变大？变化从哪个月开始的？和什么事件对得上？
3. **给建议**：最多三条，按「大概能省多少」排，每条给全
   「现在花多少 → 动它大概能省多少 → 具体怎么动」。

## 别做的

- **别对长尾类目也派子助手** —— 那是把成本花在没价值的地方
- **别在第一步就派子助手**（见上）
- **别把三份子报告原样堆给用户** —— 用户要的是你的综合判断，不是三份报告
- 子助手**只能读**。需要改分类或者记东西时，那得你自己做，而且会先问用户
