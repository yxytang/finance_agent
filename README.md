# finance_agent

个人财务分析 agent —— 自然语言问题进去，**可复现的数字**出来。

> 九天完成。`day-1` … `day-9` 九个 tag 都在。

## 三条设计原则

深度不在算法，在这三条上。它们比多写 500 行代码管用：

1. **LLM 绝不做算术。** 模型只把「上个月外卖花了多少」解析成结构化参数
   （时间范围、类目、聚合方式），数字一律由 `fa/query.py` 算。所以答案可复现，
   也不会出现模型心算 `487 + 312 = 799` 这种错 —— 而「让模型读一遍账单然后
   凭感觉说」正是这个项目要区别于的东西。
2. **概率性的部分必须可度量。** 交易分类走 LLM、检索走 RAG，所以两者都配带
   真值的评测：分类出 per-class precision/recall，检索用 RAGAS 出
   faithfulness / context_precision / context_recall。不是一个「看着还行」的 demo。
3. **隐私边界是架构约束，不是约定。** 送进 LLM 的只有归一化后的商户串
   （`STARBUCKS #1234 SEATTLE WA` → `starbucks`），不带金额、日期、账户。

## 现在能做什么

```bash
python -m data.generate     # 生成合成账单（第一次要跑）
python -m data.categorize   # 给商户归类（第一次要跑，之后走缓存）
python -m fa                # 终端里用
python -m web.server        # 或者浏览器里用 → http://127.0.0.1:8000
```

能问出**可核对**的数字，能对账，能出月度报告：

```
fa> 2026 年 7 月一共花了多少钱？

## 2026-07 收支
合计 **7,434.96**，共 87 笔。

### 环比
| 月份 | 金额 | 笔数 |
|---|---|---|
| 2026-06 | 7,274.63 | 90 |
| 2026-07 | 7,434.96 | 87 |
7 月比 6 月多 **160.33**（6 月 7,274.63 → 7 月 7,434.96），笔数反而少 3 笔。
```

工具：

| 工具 | 说明 |
|---|---|
| `describe_data` | 账单覆盖范围、账户、今天几号、分类覆盖率 |
| `query_transactions` | 筛选 + 聚合 + 分组。**所有数字的唯一来源** |
| `find_anomalies` | 重复扣款 / 订阅涨价 / 异常大额 |
| `list_subscriptions` | 固定扣款清单，按**年化**金额排序 |
| `project_spending` | 推算还没过完的月份大概会花多少。**返回的是推算值，不是账单里的数** |
| `upcoming_charges` | 未来一段时间已知的固定扣款；日期是从「上次扣款 + 周期」外推的 |
| `search_knowledge` | 查财务知识库（政策、规则、概念） |
| `investigate` | 派一个子助手做**上下文隔离**的深挖，只把结论带回来 |
| `ledger__*` | 3 个**通过 MCP** 从外部进程取的工具，见下 |
| `correct_category` | 纠正某个商户的类目（写缓存 + 写记忆，改前会问一句） |
| `remember` | 记下一条长期有用的信息，跨会话保留 |
| `use_skill` | 加载 skill 正文，或读它附带的参考文件 |

## 三类问题，三条路

这是这个 agent 最容易走错的地方：

| 问题 | 走哪条路 |
|---|---|
| 「我花了多少」「有没有被多扣钱」 | 查账单：`query_transactions` / `find_anomalies` |
| 「这个月会花多少」「下个月要扣什么」 | 推算：`project_spending` / `upcoming_charges` |
| 「房贷利息能抵多少个税」「应急资金存几个月」 | 查知识库：`search_knowledge` |
| 「我该不该买房」 | 都不适用 —— 说明它取决于哪些因素，**不硬凑一个工具** |

判断错的表现很隐蔽：**拿账单数据去回答政策问题，会给出一个看起来合理但和问题
无关的数字。** 所以这些岔路口写进了 system prompt，而不是留给模型自己领悟。

预测这条路还多一层风险：**它的产物和事实长得一模一样**。「9 月大概花 9,457」
和「9 月花了 9,457」在屏幕上没有区别，用户分不出来就会当事实用 —— 而这种错误
不会报错。所以 prompt 的铁律 4 要求推算值必须连着依据一起说。

## 知识库检索（RAG）

`knowledge/` 里是 12 篇中文个人理财文档（个税、五险一金、房贷、信用卡、保险、
征信、应急资金……），切成 **60 个块**。

**这一路是混合的。** DeepSeek 不提供 embedding 接口（查证过），所以词法那两路
没有向量召回 —— 第十一天用阿里云百炼的 embedding 补上了第三路，并在融合之后
叠了一层 cross-encoder 重排。**没配 `RAG_API_KEY` 就自动退回纯词法两路**，
行为和加向量之前逐字节一样。

### 检索管线

1. **按标题切块**，每块带 breadcrumb（`个税基础.md > 专项附加扣除 > 住房贷款利息`）
2. **两路 BM25**：一路查 breadcrumb，一路查正文。
   中文用**字符 bigram**（不分词），外加停用词过滤
3. **一路向量**（可选）：父块再递归切成子块，嵌的是**子块**（更准），
   命中之后回溯到**父块**（上下文更全）
4. **RRF 融合**：只用名次不用分数，因为几路的分数不可比
5. **cross-encoder 重排**（可选）：把融合出来的前 20 个候选逐个重排

### 实测数字

```bash
python -m eval.retrieval --mode bm25            # 词法基线：确定、免费、秒级
python -m eval.retrieval --mode full            # 加向量
python -m eval.retrieval --mode full --rerank   # 再加重排
```

| 模式 | 字面 文件@1 | 字面 小节@1 | 换说法 文件@1 | 换说法 进前三 |
|---|---|---|---|---|
| bm25 | 14/15 | 10/15 | 1/5 | 3/5 |
| full | 14/15 | **13/15** | **3/5** | 3/5 |
| full + 重排 | 14/15 | **13/15** | 3/5 | **4/5** |

朴素 grep 基线：字面 11/15、换说法 2/5 —— 三种模式都比它强。

两组问题的失败原因**完全不同**，所以分开报：

**字面组一直是「排得不够靠前」，不是「找不到」。** 加向量把小节@1 从 10/15
提到 13/15；再加一层重排，期望文档 15/15 全部进前三。文件@1 那道失分
（「货币基金能随时取吗」落到 `应急资金.md`）三种模式都一样 —— 那是语料本身的
问题，不是排序问题。

**转述组原来那条 1/5 才是词法检索的结构性短板。** 问「怎么少交点税」，文档里
写的是「专项附加扣除」，字面上一个词都对不上 —— 这**不是 bug，是纯词法检索的
定义**。向量那一路把它提到 3/5。

⚠️ **但转述组在 RAGAS 报告里的低分主要不在这。** 那 4 道题里有 3 道 agent
压根没调用检索，检索层怎么改都执行不到 —— 那是**路由**问题，和这里说的是
两码事。详见 [findings.md](findings.md) 的根因那节。

### 一个量过的负面结论：多查询改写没用

第十一天本来还想加一层 query rewrite（多查询扩展、HyDE 那类），**量完没上**。
五种写法在完整管线上**一个字都不变**：

```
                     字面组            换说法组
原句（基线）        @14/15 均1.07    @3/5 均2.20
关键词 3 组         @14/15 均1.07    @3/5 均2.20
关键词 1 组         @14/15 均1.07    @3/5 均2.20
HyDE + 原句         @14/15 均1.07    @3/5 均2.20
HyDE 单独           @14/15 均1.07    @3/5 均2.60   ← 还更差
```

对照实验说清了机制：**纯 BM25 下改写把转述组从 1/5 提到 3/5 —— 正好是向量达到
的那个数。** 也就是说改写和向量补的是同一个洞：它不是「再加一层」，是向量的
廉价替代品。（而且纯 BM25 下改写会把字面组从 14/15 打到 11/15，因为变体查询
是关键词式的，把原来那句精确的问法稀释了。）

管线里已经有向量 + 重排时，改写的价值被整个吸收掉了 —— 只会每次检索多烧一次
LLM 调用。所以它不在代码里。

### 一个不修就会静默出错的坑

索引带**语料指纹**（文件名 + 大小 + 修改时间的纳秒值 + 分词方案版本号），
语料一变就重建。少了它，表现是「明明写了这段、却搜不到」—— 没有报错，
看起来就像「知识库里没有」。

指纹里必须带**分词方案版本号**：改了分词逻辑而语料没动的话，指纹不变、
索引不重建，检索会继续用旧方案的排名。

## 子 agent：上下文隔离

`investigate` 派一个子助手去深挖一件具体的事，**只把结论带回来**。

```bash
python -m eval.delegation
```

```
任务：帮我分析一下我的消费，看看哪里可以省

  主上下文总计               14,029 字符
  子助手内部过程合计         27,247 字符   ← 没有进主上下文
  回传给主 agent 的           6,569 字符
  ─────────────────────────────────
  省下                       20,678 字符
```

不隔离的话，主上下文会是 **约 34,700 字符**（14,029 + 20,678）。现在是 14,029 ——
**降到 40%**，而且这个收益**后面每一轮都在拿**。

### 隔离才是价值，不是并行

这两件事经常被混着说，但收益完全不同：并行省的是**时间**（一次子任务也就十几秒），
隔离省的是**上下文**，而且是每轮都在省。

所以判断要不要开子 agent，标准不是「能不能并行」，而是
**「这个子任务的中间过程有没有价值」**。

中间结果**本身就是答案**的时候（「把这 20 笔列出来」），开子 agent 反而有害 ——
结论就是中间结果，隔离之后信息反而丢了。所以工具描述里两个方向都写了。

### 什么写死在代码里，什么交给模型

**能力边界写死，使用决策交给模型。**

| 写死在代码里 | 交给模型 |
|---|---|
| 子 agent 的工具集**只读**（不能改分类、不能写记忆） | 什么时候该开 |
| **白名单**，新加的工具默认不给子 agent | 子任务怎么切 |
| 不给它 `investigate` 自己（递归是失控的乘数） | |
| 步数上限 10（主 agent 是 24） | |

前四项不是判断题，是安全边界 —— 子 agent 的中间过程用户看不到，
**未经确认的写操作不该从一个没人看的上下文里发生**。后两项才真正需要判断力，
而且模型手上有足够的信息（它知道主上下文里已经有什么）。

步数上限给低，是为了让「任务没切好」**尽早暴露**：切得对的问题几步就回来了，
切得太宽的问题会撞上限然后如实说「我没做完」—— 而那是主 agent 需要知道的信号。

### 工作流写成了 skill

`skills/spending-review/SKILL.md` 描述了三步：**先摸清结构（不派子助手）
→ 逐类目深挖（派子助手）→ 综合（不派子助手）**。

第一步明确写「不要派」：那一步的结果主 agent 自己已经看到了，派出去等于把
它查的东西又隔离掉，还得再问一遍。实测模型照做了。

## MCP：自己写一个 server

`mcp_server/ledger_server.py` 把账单包成一个 MCP server，`fa/mcp/` 是**手写的**
JSON-RPC 客户端（不装 SDK）。`/mcp` 可以现场看一遍握手：

```
fa> /mcp
  服务端：ledger 0.1.0
  协商到协议版本：2024-11-05
  运行时发现 3 个工具：
  list_accounts          （无参数）
  list_merchants         limit
  fetch_transactions     date_from, date_to, account, limit
```

三步：`initialize` 能力协商 → `tools/list` 发现 → `tools/call` 调用。
**工具是运行时读到的，不是编译进客户端的** —— 换一个 server、加一个工具，
客户端一行都不用改。这就是它比「每家自己写 plugin」强的地方。

### 独立进程让边界变成真的

在同一个进程里，「不把金额发给 LLM」只是一句约定 —— 任何一处忘了检查就漏了，
而且没有症状。跨进程之后，**server 不返回的东西，agent 拿不到**，不是「不该拿」。

`list_merchants` 就是这条边界的执行点：归类只需要商户串，所以它就只给商户串。
测试直接钉住这一点（`tests/test_mcp.py`）：

```python
assert not re.search(r"\d+\.\d{2}", out)          # 没有金额
assert not re.search(r"\d{4}-\d{2}-\d{2}", out)   # 没有日期
assert "credit" not in out and "checking" not in out  # 没有账户
```

### 它不是内置工具的重复

`fetch_transactions` 填的是一个**真实空缺**：内置的 `query_transactions` 只能
聚合（合计/笔数/分组），**列不出原始明细**。实测问「把 2026-03-14 那天的交易
逐笔列出来」，模型正确地走了 `ledger__fetch_transactions`，而且顺手发现了
那天的一笔重复扣款 —— 那是 Day 1 埋在数据里的坑。

### 两个传输层的坑

**stdout 是协议通道**，server 里一个多余的 `print` 就会把协议搅坏 —— 混进去的
那行会被当成 JSON-RPC 消息解析，表现为「server 忽然不响应了」。所以调试输出
一律走 stderr。

**stderr 不能接管道而不读**：服务端写满管道缓冲区就会阻塞在写 stderr 上，
而客户端在等它的 stdout —— 双方互相等，死锁。客户端让 stderr 直接继承，
顺带日志直接打在控制台上。

## RAG 评价：用 RAGAS 量过检索质量

```bash
python -m eval.collect      # 跑 agent，记下每次检索到什么
python -m eval.ragas_run    # 跑三个指标，写 findings.md
```

`eval/qa_cases.py` 里是 21 道题，**参考答案是人工照着语料逐条核对写的** ——
这是 RAGAS 能不能信的前提。参考答案要是生成的，这个评测就变成了「模型 A 的
答案 vs 模型 B 的检索」，而且会自证：检索得好、答案也答得好，分数虚高而没人知道。

### 三个指标的分工

| 指标 | 测哪一端 | 低了说明 |
|---|---|---|
| `faithfulness` | **生成端** | 答案超出了检索到的内容 —— 模型在编 |
| `context_precision` | 检索端 | 排在前面的块没用 —— 排序不好 |
| `context_recall` | 检索端 | 该有的块没被检索到 —— 漏了 |

这个分工是重点：**分数低的时候，你能分清是检索的锅还是生成的锅。**

### 结果（21 题）

| 组 | faithfulness | context_precision | context_recall |
|---|---|---|---|
| 字面问法（17 题） | 0.80 | 0.83 | **1.00** |
| 换种说法（4 题） | 0.48 | 0.40 | 0.42 |

第十一天之前的同一份评测：字面 `0.74 / 0.80 / 0.88`，换种说法 `0.02 / 0.25 / 0.25`。

完整报告在 [findings.md](findings.md)。

### 最值得说的发现：**改一句提示词，比改检索器管用**

Day 8 量到一个反直觉的结论：转述组那 4 道题里只有 1 道真的调了检索，
**失分在路由不在检索**。那个诊断为后面省下大量白工 —— 三个指标一起塌的时候，
最自然的反应是去调排序、换分词、上向量，但如果 agent 压根不调用检索，
**那些改动一个都不会让分数上升**。

第十一天这件事变了，而且是意外发现的：

```
             真的调了检索（换种说法 4 题）
Day 8         1/4
第十一天       3/4
```

**变的不是检索器，是 `search_knowledge` 的一句 docstring。** 它原文写着
「这个检索是纯词法的（没有语义向量），换个说法就搜不到」—— 我删掉它是因为
加了向量之后前半句是假话，**结果后半句在劝模型别搜**。删掉之后，agent 对
「怎么才能少交点税」这种问题开始主动检索，而且写的是自然语句
（`工资薪金个人所得税 累计预扣预缴 为什么每月扣税不一样`）而不是硬凑的关键词。

⚠️ **这次的提升混了两个改动，分不开。** 字面 `context_recall` 从 0.88 到 1.00
可以确定是检索层的功劳（路由一直是 17/17）；但换说法那组的提升里，
有多少是向量、有多少是那句 docstring 松开了路由，这一轮跑分不开。
要分的话得拿「新 docstring + 纯 BM25」再采集一次。

（这条也修正了 Day 5 的一个判断：当时拿原始问题直接查检索器，转述组 1/5，
我写的是「纯词法检索的结构性短板」。补上那个缺口的是 **agent 自己的改写**，
不是检索层 —— 第十一天专门量过：给检索层再加一层 query rewrite，在已经有
向量的管线上一个字都不变。见上面「检索」那节的负面结论。）

所以 `findings.md` 里那节根因分析是**算出来的**，不是写死的 ——
写死的结论会随数据变化变成谎言，而它看起来仍然像一份分析。

### 一个差点上线的假结果

第一版跑出来是 `faithfulness 0.10 / precision 0.06 / **recall 0.00**`。

没有任何报错，进度条正常走完，分数落在合理区间 —— **它长得非常像真结果**。
起疑的唯一原因是两个数对不上：本地算出「检索到正确文档 17/17」，
而 recall 是 0.00。

查下去是我的 bug：采集脚本只记了块的**标题**没记**正文**。喂给 RAGAS 的
`retrieved_contexts` 是一堆光秃秃的小节名，里面没有答案需要的任何事实。
修完块的平均长度从 35 字符变成 203.8 字符。

现在有一道防呆（`sanity_problem`）会在跑之前检查上下文长度，太短就拒绝跑。

**一个静默的错误指标比没有指标更糟** —— 你会照着它去优化错的地方。

## Web 前端

```bash
python -m web.server        # http://127.0.0.1:8000
```

单文件 HTML、原生 JS、零构建。唯一的 CDN 依赖是 Chart.js —— 离线时图不出，
但对话照常。

### agent 的界面不是聊天的界面

一轮要跑几十秒，中间有多次工具往返。普通聊天那种「转圈等两秒」的做法在这里
会让用户完全失去判断力：**他不知道 agent 是在干活还是卡住了，也不知道它有没有
走偏。**

所以工具调用是**一等公民**，实时冒出来：

```
→ describe_data
→ use_skill(monthly-report)
→ query_transactions(group_by=category)   ← 分组结果自动出图
→ ... → 答案（合计 7,434.96）
```

分组结果会**自动出图**：柱状图（按数值排的）或折线图（按时间排的），
识别不出分组就只显示文字。

### 实时推送用 SSE 而不是 WebSocket

agent 的事件是**单向**的（服务端推、浏览器收），SSE 恰好就是为这个设计的：
不用维护连接状态机、**浏览器自动重连**、就是一个普通 HTTP 响应（没有协议升级
握手，代理和防火墙对它更友好）。WebSocket 是双向的，这里用不上另一半，
却要接管它全部的生命周期。

### 权限确认怎么跨 HTTP 工作

`correct_category` 改数据前会先问一句（Day 4 定的），而那个回调是**同步**的 ——
它在 `session.send()` 里被调用，必须当场返回 bool。浏览器却是异步的。

用一条阻塞等待把两边接起来：

```
工具线程                        浏览器
confirm() 被调用
  推 confirm_request 事件 ──▶   弹出确认框
  event.wait(timeout=300)       …用户想几秒…
  ◀───────────────────────────  POST /confirm
  返回 True/False
```

**超时即拒绝。** 浏览器关掉了、网络断了、用户走开了 —— 这些情况下等待必须结束，
而且必须结束在「不允许」那一侧。一个等不到答复就放行的实现，等于把确认这件事
取消了。

实测的事件序列：

```
tool_call(correct_category) → confirm_request ←（工具线程在这里停住）
                            → [点了允许] → tool_result(已改)
```

### 刷新页面历史还在

SSE 没有回放 —— 刷新之后新连接是「从此刻起」的，而 agent 可能已经跑了一半。
所以每个会话留一份事件日志，新连接**先回放再续播**。日志有上限（2000 条），
超了丢最老的。

## 部署

### 有写权限的 agent 不能裸放公网

这个 agent 能改分类缓存、写长期记忆、跑子 agent。挂到公网上不加防护，等于给
每个路过的人一个能改你数据的对话框。三件事各挡不同的东西：

| | 挡什么 | 这个项目里的做法 |
|---|---|---|
| **访问控制** | 谁能用 | `FINANCE_WEB_TOKEN` 环境变量。**设了就要求带** |
| **限流** | 用多快 | 每会话每分钟 6 轮（可调）。每次提问都是真金白银的 LLM 调用 |
| **会话隔离** | 能碰到什么 | 每会话一个独立 `Session`；上限 50 个 |

**默认只监听 `127.0.0.1`。** 想对外开的话：

```bash
FINANCE_WEB_TOKEN=换成你自己的随机串 python -m web.server --host 0.0.0.0 --port 8000
```

### 还没做的（写出来，而不是假装都有）

- **没有 HTTPS**。token 放在 URL query 里会进日志和 Referer，正确做法是配
  TLS 然后走 `Authorization` 头。这个项目没配。
- **限流是内存里的**，重启就清空，多进程部署时每个进程各算各的。
- **一个用户能看到的会话是全局的** —— 没有「这个 token 只能访问它自己开的会话」
  这层隔离。
- **没有会话过期**，会一直堆在内存里直到进程重启。

前三条各自都有标准做法（反代 + TLS、Redis 计数、会话绑定 token），但那是部署
工程而不是这个项目的重点。**写出来是因为「部署了」这三个字会让人以为该有的
都有。**

## 还没做的

- `import_csv` 那个工具**没做**，是有意的：那意味着接受一个**文件路径**参数的
  工具，而这个项目的设计是模型永远不提供路径（见下面「已经定下来的设计」）。
  数据从哪来是部署时的事，不是运行时由模型决定的事。

## 交易分类：三层，而且都被量过

银行流水的商户串是给人看的，不是给机器比的（`AMZN Mktp US*2H4KJ`）。所以先
**归一化**，再过三层：

| 层 | 速度 | 花钱 | 覆盖率 |
|---|---|---|---|
| 规则 | 微秒 | 不花 | 低 —— 只敢覆盖常见且无歧义的 13 个商户 |
| 缓存 | 微秒 | 不花 | 中，随用随长 |
| LLM | 秒级 | 花 | 全覆盖 |

**顺序是「规则 → 缓存 → LLM」，不是「缓存 → 规则」。** 差别只有一句话：
改规则要能立刻生效。缓存先查的话，一条写错的规则被缓存固化之后就再也改不回来，
而且没有任何症状。所以**缓存只写 LLM 的结论，不写规则的结论**。

分类是**批处理**（`python -m data.categorize`），不是查询时现算 —— 用户不该为了
问一句「上个月花了多少」等一次 LLM 调用。

```bash
python -m data.categorize            # 分类并把缓存写回去
python -m data.categorize --report   # 顺带出 per-class 报告
```

### 实测数字

| 场景 | 商户 | LLM 调用 | 缓存命中 | accuracy |
|---|---|---|---|---|
| 冷启动（空缓存） | 36 | **1 次** | 0% | **97.1%** |
| 再跑一次 | 36 | **0 次** | 100% | 97.1% |
| 用户纠正一次之后 | 36 | 0 次 | 100% | **99.9%** |

冷启动那次 36 个商户只发**一次**批量调用。97.1% 里的全部损失来自**一个**商户：
`TARGET` 被判成了「超市」，而它在这个账单里是「购物」—— 一次判断错，
**32 笔交易跟着错**。

> 这就是商户级归类的杠杆：判对一次省几百次调用，判错一次错几百笔。
> 也因此 `correct_category` 值得存在 —— 用户改**一次**，修好 32 笔。

剩下那 1 笔是 `GEICO AUTO INSURANCE`（年度车险判成「其他」，真值是「交通」）——
保险算不算交通本来就可争议，这个错误保留着不修，它是真实存在的边界情况。

## 跨会话记忆

记忆就是 `memory/facts.md` 一个 markdown 文件，**可以直接编辑**：

```markdown
- 2026-09-21 [偏好] GEICO 车险是每年固定交一次的年度支出，不要报成异常。
- 2026-09-21 [纠正] target 归「购物」而不是「超市」
```

做成可读文件不是为了省事：**记忆出错的时候用户得能自己修**。存在数据库里、
要写脚本才能改的话，一条记错的偏好会一直跟着他。

用 `/memory` 查看，`/memory rm N` 删一条。

**难点在「什么时候记」，不在「记在哪」。** 一次性的任务细节（「这次看看 3 月」）
记下来，下次用户问 4 月时它就是错的 —— 而且看起来还挺合理，特别难发现。
所以 `fa/memory/extract.py` 有一道门槛，拒绝时还会说明理由（不说明的话模型会
换个说法再试一次，那比一开始放行更糟）。

**用户纠正一次分类 = 最自然的记忆写入入口**，所以 `correct_category` 同时写
缓存（现在就生效）和记忆（以后答得出为什么）。

## skill：三个财务工作流

`skills/<名字>/SKILL.md`，frontmatter 全是可选的（`name` 缺省取目录名，
`description` 缺省取正文第一行）。

| 级 | 进上下文的东西 | 什么时候 |
|---|---|---|
| 1 | name + description | 每轮，一直在 system prompt 里 |
| 2 | SKILL.md 正文 | 模型调 `use_skill(name=...)` 时 |
| 3 | `references/` 下的文件 | 模型调 `use_skill(name=..., path=...)` 时 |

第一级只有 **1108 字节**（预算 1500），而且**每一轮都在** prompt 里 ——
这就是为什么正文不能跟着一起进去。用 `/skills` 可以看当前清单和它的字节数。

三个 skill 的**触发场景刻意不重叠**，否则模型挑不对：

| skill | 什么时候用 |
|---|---|
| `monthly-report` | 「这个月花了多少」「月报」「上个月怎么样」 |
| `reconcile` | 「有没有乱扣钱」「账单正常吗」「帮我查查」 |
| `budget-check` | 「怎么省钱」「哪里花多了」「预算超了吗」 |

`reconcile` 的第三级 `references/playbook.md` 专门讲**怎么把「离群」和
「真有问题」分开** —— 检测器报的是「这笔比同组的其他笔大得多」，它没有说
这笔有问题。分不清就直说分不清，含混地报「发现异常」会让用户跑去和商户吵架。

## 数据是合成的

`data/transactions.csv` 由 `data/generate.py` 生成：起点固定 `2025-09-01`，
**结束日跟今天走**，种子固定。商户名照着真实银行流水的样子写
（`AMZN Mktp US*2H4KJ`、`TST* SUSHI PALACE`、`UBER *TRIP`）。

**结束日为什么跟今天走**：这样「本月」在数据里真实存在 —— 预测类功能需要一个
当下的靶子，否则「这个月还没过完」这条边界永远只能在纸面上讨论。代价是数据
不再随时间不变：复现某次分析靠的是**同 seed + 同结束日**，用
`python -m data.generate --end 2026-09-22` 把当时那天钉回去。

延长结束日只会**追加** —— 前面的月份一笔都不变（`end` 不参与抽样，换个结束日
拿到的永远是同一条随机序列的前缀）。6 个坑因此不会被挤走，`--check` 会看着。

### 金额符号约定：支出为正

⚠️ **银行流水一般是反过来的。** 这里选「支出为正」，因为「上个月花了多少」
直接求和才是直觉的；反过来则每个查询都得先取负号，迟早有一处漏了。
读代码或接真实数据前请先记住这一条 —— 它反直觉，不看文档一定会猜错。

### 埋了 6 个坑

它们是后面所有评测的真值。`--check` 会**从产物里反查**它们还在不在 ——
不是靠生成时的断言，因为断言只能证明「我打算埋」，反查才能证明「埋进去了」。

```bash
python -m data.generate --check
```

| # | 坑 | 考的是什么 |
|---|---|---|
| 1 | 同一商户同一天同金额扣两次（非订阅） | 重复扣款检出 |
| 2 | Netflix 从第 7 个月起涨价 25% | 订阅涨价检出 |
| 3 | 一笔购物是同类目 p95 的 15 倍 | 异常大额检出 |
| 4 | 一个每月 9.99、名字不显眼的订阅 | 幽灵订阅检出 |
| 5 | 一笔 −139.99 的退款 | 金额符号处理 |
| 6 | 同一个商户的金额从 4.99 跨到 329 | 分类的边界 |

## 已经定下来的设计

- **金额用 `Decimal` 不用 `float`**，而且外部输入一律先转字符串 ——
  `Decimal(0.1)` 接到的已经是个二进制近似值了（`fa/models.py`）
- **`Transaction` 是冻结的**：改类目用 `with_category()` 产出一条新的，
  「改之前是什么样」永远还在，分类评测要的正是这个
- **真值和输入分两个文件**：`transactions.csv` 不含类目（泄题），
  `reference.csv` 才是答案
- **ingest 刻意不做 txn_id 去重**：那会让「重复」出现两个打架的定义
- **`query.py` 是纯函数**，而且**返回结构化结果不是字符串** —— 一个返回字符串的
  查询引擎没法当 oracle：你得反过来解析自己渲染的文本才能拿到数字，
  那是在测试渲染器，不是在测试查询
- **日期范围是闭区间**：用户说「7 月」，7 月 31 号那天的消费当然要算进去
- **查询参数里的类目必须校验**：传一个不存在的类目不会报错，只会返回 0 笔 ——
  然后模型会自信地告诉用户「你这个月没吃饭」。**错的枚举安静地返回空**，
  是最难发现的一类错误
- **异常检测用 Tukey 围栏（Q3 + 3×IQR），不用 p95**：p95 按定义就标出 5% 的
  交易（账单上千笔，那就是几十笔）。一个标出几十笔的检测等于没有检测 ——
  用户看两次就学会无视它，之后真正的那一笔也一起被无视
- **订阅识别要同时卡「金额固定」和「间隔规律」**：只卡前者，一杯 5.00 的咖啡
  一年里恰好买到 4 次同样金额，和订阅长得一模一样
- **让模型主动做的事写在工具描述里，不写在 system prompt 里** —— 实测过：
  只写后者，模型连着几个任务都不会照做
- **会安静返回错答案的参数必须拦**：类目名打错返回 0 笔、未分类数据按类目查
  返回 0 笔，二者都和「真的没花这个钱」长得一模一样，用户无法察觉

## 在合成账单上的实测数字

`python -m pytest` 之外，这四个数字是拿真账单跑出来的（Day 2 验收）：

| 埋的坑 | 检测器 | 结果 |
|---|---|---|
| 1 重复扣款 | `find_duplicates` | 检出 1 组，**误报 0** |
| 2 订阅涨价 | `find_price_increases` | 检出 1 个（NETFLIX 15.49 → 19.36），**误报 0** |
| 3 异常大额 | `find_outliers(group_by="category")` | 检出 2 笔 |
| 4 幽灵订阅 | `find_subscriptions` | 在清单里，年化 119.88（月付仅 9.99） |
| 5 负数退款 | `query(agg="min")` | −139.99 |

第 3 项检出 2 笔而不是 1 笔，不是误报：另一笔是年度车险 742 元，它落在「交通」

这笔值得记下来，因为它说明检测器在找「离群」而不是「我埋的那一笔」。

## 骨架来自一个编码 agent 项目

`fa/` 里的 `events.py`、`agent.py`、`skills.py`、`permissions.py` 是从我另一个
编码 agent 项目（`forge`）搬过来的 —— 那些部分和领域无关，任何 agent 都要：
多轮循环、事件回调、三级渐进披露、权限回调。

**搬的时候丢掉了工作区路径边界。** 那个编码 agent 需要它，因为它的模型能传任意
文件路径进来；这里的模型**不接收任何路径**（读账单是账单服务的事，读知识库是
ingest 的事）。没有入口，就不需要守门 —— 留着不用的守门代码最大的害处不是占
地方，是下一个人会以为它有意义，然后在一个不需要它的地方维护它。
